## 개정 이력

- 2026-11-11 (사용자 피드백): 첫 구현은 송금 → 확인 중 → 사용자가 "다시 확인" → 결과였다. 결과를 보려면 한 번 더 눌러야 해 UX가 나쁘다.
  - 바꾼 흐름: **보내기 → 로딩 → 결과(보냈어요 / 송금 실패 + 사유).** 재시도 뒤에도 모르면 앱이 키로 **자동 조회**한다.
  - 조회마저 실패하는 드문 경우만 "결과를 확인하지 못했어요" 결과 화면을 보여 준다. 버튼은 "확인" 하나 (사용자 결정).
  - "확인 중" 화면과 "다시 확인" 버튼은 없앴다. 아래 본문은 개정된 내용이다.

## 1. 의도와 이유

- 사용자가 정한 "트랜잭션 관리"의 뜻: **송금 정합성.** APM 추적, 로컬 DB 트랜잭션은 이 세션에서 다루지 않는다.
- 성공 기준 (사용자 확인):
  1. "보내기"를 몇 번 누르든, 응답이 깨지든 끊기든 **돈은 정확히 한 번만** 빠진다.
  2. 화면 결과는 **서버의 실제 결과와 어긋나지 않는다.**
- 지금 이 기준을 어기는 곳 (앞선 세션들의 기록):
  - `TransferModel.submit()`에 진행 중 확인이 없다. "보내기"를 연달아 누르면 송금 요청이 두 번 간다. (`ConfirmView`가 탭마다 `Task`를 만든다.)
  - 200 응답 뒤 디코딩이 실패하면 화면은 "송금 실패"인데 서버는 이미 잔액을 뺐다. (디코딩 연습 1회차에서 재현)
  - 500·404·400·네트워크 오류가 모두 `.failure` 하나로 표시된다. 서버가 처리했는지 모르는 경우와 거절한 경우가 섞인다.
  - 가짜 서버에 같은 요청을 알아보는 수단(멱등 키)이 없다. 그래서 재시도를 넣으면 돈이 두 번 빠진다.

## 2. 목표

1. 송금 한 건에 **송금 키** 하나. 서버는 같은 키를 다시 받으면 돈을 빼지 않고 첫 결과를 돌려준다.
2. 송금 중에는 다시 보낼 수 없다.
3. 송금 중에는 로딩을 보여 주고, 결과는 **보냈어요 / 송금 실패(이유)** 로 끝낸다. 조회마저 실패하면 **결과를 확인하지 못했어요.**
4. 서버가 처리했는지 모르는 실패는 같은 키로 **자동 재시도**한다.
5. 재시도 뒤에도 모르면 앱이 키로 **자동 조회**한다. 조회는 송금을 새로 만들지 않는다. 사용자가 따로 누를 것은 없다.
6. 위 동작을 재현할 실패 주입을 가짜 서버와 실행 인자에 추가한다.
7. 단위·통합·UI 테스트와 시뮬레이터 확인을 `CLAUDE.md` 테스트 규칙대로 함께 쓴다.

## 3. 비목표

| 하지 않는 것 | 이유 |
|---|---|
| 앱을 껐다 켜도 "결과를 확인하지 못한" 송금을 기억 | 로컬 저장소가 필요하다. 로컬 DB 주제다 (사용자 확인) |
| 잔액·금액 로그 `.public` 정리 | 개인정보 문제라 정합성과 별개다 (사용자 확인) |
| 가짜 서버 전역 등록(`FakeBackend.makeSession`) 개선 | 기존 규칙(`@Suite(.serialized)`)으로 충분하면 손대지 않는다 (사용자 확인) |
| APM 구간 추적, 성능 측정 | 다른 주제. 성능 세션이 따로 진행 중이다 |
| `submit()`에서 `canProceed` 재확인 | 지금 UI에는 확인 화면 뒤 금액이 바뀌는 경로가 없다. 서버가 400으로 거절하고, 이제 그 거절이 이유와 함께 표시된다 **(제 판단)** |
| 같은 키 요청이 동시에 처리 중일 때의 응답(409) | `FakeServer`는 `Mutex`로 요청을 하나씩 처리한다. 동시 처리 상태가 생기지 않는다 **(제 판단)** |
| 송금 키 만료 | 가짜 서버는 앱 실행 동안만 산다 **(제 판단)** |
| 송금 요청 대기 상한(시간 초과) 조정 | 가짜 서버는 멈추지 않는다. `URLSession` 기본값(60초)을 그대로 둔다. 세션 설정을 바꾸면 홈 조회와 성능 주제에 닿는다 **(제 판단)** |
| 홈 화면 변경 | 홈은 송금 창이 닫힐 때 이미 잔액을 다시 불러온다 (`RootView`의 `onDismiss`) |
| 외부 라이브러리 | 필요 없다 |

## 4. 안티 목표 (돌아가도 실패로 보는 것)

- 서버가 처리했는지 모르는데 "송금 실패"라고 보여 준다.
- 재시도나 자동 조회 때문에 돈이 두 번 빠진다.
- 결과를 보려고 사용자가 한 번 더 눌러야 한다 (개정 이력).
- 송금 키 없이 재시도한다.
- 재시도 대기 때문에 테스트가 느려지거나 불안정해진다. 단위·통합 테스트는 대기 0으로 돈다.
- 다른 주제(성능, 로그 개인정보, 로컬 DB)를 미리 구현한다.

## 5. 제약

- 모듈 경계: Feature끼리 import 금지, Domain은 SwiftUI·네트워크 import 금지. 화면 로직은 `@Observable` 모델에 두고 뷰는 표시만 한다.
- `BankingRepository` 프로토콜이 바뀌면 `HomeFeature`와 `TransferFeature`의 `StubBankingRepository` 둘 다 맞춘다.
- 테스트 규칙은 `CLAUDE.md` `## 테스트` 그대로다.
  - 버그 수정은 재현 테스트를 먼저 쓴다. 이 작업에서는 "연타 시 요청 2번", "200 + 디코딩 실패가 송금 실패로 표시"가 해당한다.
  - `FakeBackend.makeSession`을 부르는 테스트는 그 타깃의 `@Suite(.serialized)`에만 둔다.
  - 테스트의 가짜 서버는 `FakeServer(latency: .zero)`.
  - UI 테스트는 고정 sleep 금지, `waitForExistence`.
- 기존 실행 인자 `--fail-transfer`는 계속 동작한다. 의미(처리 전 500)도 그대로다. 화면 결과만 바뀐다(§6.5).
- `CLAUDE.md`: `## 트랜잭션` 섹션을 새로 쓴다. 기존 줄은 동작이 바뀐 곳만 고친다: `--fail-transfer` 설명, 로그 표의 `transfer` 행, 테스트 개수. 성능 세션이 같은 파일을 고칠 수 있으니 수정 범위를 좁힌다.
- 공개 저장소다. 커밋에 키·토큰·개인 경로를 넣지 않는다.
- `docs/debugging-drills.md`는 지난 연습 기록이라 고치지 않는다. 1회차 증상("송금 실패인데 잔액이 빠짐")은 이 작업 뒤로 "보냈어요"로 바뀐다 **(제 판단)**.

## 6. 결정된 것

### 6.1 송금 키

- 송금 한 건 = 키 하나. 자동 재시도와 자동 조회는 모두 같은 키를 쓴다.
- 생성 시점: `proceedToConfirm()`을 통과할 때 새 UUID 문자열 **(제 판단)**. 확인 화면에서 뒤로 가 금액을 바꾸고 다시 들어오면 새 키다. 아직 아무것도 보내지 않았으므로 안전하다.
- 전달: HTTP 헤더 `Idempotency-Key` **(제 판단)**. IETF 초안과 결제 API들이 쓰는 이름이다. 본문 `TransferRequest`는 바꾸지 않는다.
- 저장소 프로토콜 (Domain) **(제 판단)**:
  - 송금: 요청과 키를 함께 받는다.
  - 조회: 키로 영수증을 찾는다. 없으면(404) `nil`.
  - 정확한 이름·시그니처는 빌더가 정한다.

### 6.2 가짜 서버 계약

`POST /transfers` 판정 순서 (위에서부터):

| 순서 | 조건 | 응답 | 잔액 |
|---|---|---|---|
| 1 | 실패 주입 "처리 전 거절" (`--fail-transfer`) | 500 | 그대로 |
| 2 | `Idempotency-Key` 헤더 없음 **(제 판단: 키 필수)** | 400 | 그대로 |
| 3 | 본문 없음·디코딩 실패 | 400 | 그대로 |
| 4 | 같은 키 기록이 있고 본문이 같음 | 200 + 저장된 영수증 | 그대로 |
| 4 | 같은 키 기록이 있고 본문이 다름 | 422 **(제 판단)** | 그대로 |
| 5 | 모르는 출금 계좌 또는 받는 사람 | 404 | 그대로 |
| 6 | 금액 무효 (0 이하, 잔액 초과) | 400 | 그대로 |
| 7 | 처리 | 200 + 영수증. 영수증을 키로 저장 | 차감 |

- **4는 반드시 5·6보다 먼저다.** 첫 요청이 처리된 뒤 재시도가 오면 잔액은 이미 줄어 있다. 금액 검사를 먼저 하면 처리된 송금에 400을 답하고, 앱은 "송금 실패"를 보여 준다. 이 순서를 테스트로 고정한다.
- 새 경로 `GET /transfers/<키>`: 저장된 영수증이 있으면 200 + 영수증, 없으면 404. 실패 주입의 영향을 받지 않는다.
- 판정은 지금처럼 `Mutex` 안에서 한다. 같은 키 요청이 동시에 와도 하나씩 처리된다.

### 6.3 실패 주입 (재현용) **(제 판단)**

| 실행 인자 | 서버 동작 | 기대 화면 |
|---|---|---|
| `--fail-transfer` (기존) | 처리 전 500, 매번 | 로딩 → 송금 실패 "보내지 않았어요". 잔액 그대로 |
| 응답 유실 한 번 | 처리한 뒤 첫 응답만 전송 오류로 끊음 | 자동 재시도가 영수증을 받아 보냈어요. 잔액 한 번 차감 |
| 응답 유실 매번 | 처리한 뒤 `POST /transfers` 응답을 매번 전송 오류로 끊음 | 로딩 → 보냈어요 (자동 조회가 찾음). 잔액 한 번 차감 |
| 깨진 응답 | 처리한 뒤 200 + 디코딩 불가 본문 | 보냈어요 (남은 잔액 줄 없음). 잔액 한 번 차감 |

- "전송 오류"는 앱 쪽에서 `URLError`로 보이는 연결 끊김이다. HTTP 상태 코드가 아니다.
- 인자 이름과 `FakeServer`·`FakeServerURLProtocol` 안의 구현 방식은 빌더가 정한다.

### 6.4 앱 동작 (`TransferModel`)

**송금 중**
- 송금 중 상태를 모델이 가진다. 송금 중에 `submit()`이 다시 불리면 무시하고 로그를 남긴다.
- 결과가 이미 나온 뒤의 `submit()`도 무시한다 **(제 판단)**. 한 모델 = 송금 한 건이다.
- 확인 화면: 송금 중에는 **로딩**("보내는 중이에요")을 화면 전체에 덮고, "보내기" 비활성, 뒤로 가기 숨김, 시트를 끌어내려 닫기 막음 **(제 판단)**. 송금 중에 창이 닫히면 홈이 송금 반영 전 잔액을 불러와 기준 2를 어긴다.
- 송금 중은 재시도와 자동 조회가 모두 끝날 때까지다.

**결과 분류**

| 응답 | 서버가 처리했나 | 재시도 | 화면 |
|---|---|---|---|
| 2xx + 정상 본문 | 했음 | 없음 | 보냈어요 + 남은 잔액 |
| 2xx + 디코딩 실패 | 했음 | 없음 (같은 응답이 다시 온다) | 보냈어요. 남은 잔액 줄 없음 |
| 4xx | 안 함, 확정 | 없음 | 송금 실패 + 이유 |
| 5xx, 전송 오류 | 모름 | 같은 키로 최대 2회 (요청 총 3번) | 재시도 뒤에도 모르면 자동 조회 (아래) |
| 그 밖의 오류 (취소 등) | 모름 | 5xx와 같음 **(제 판단)** | 5xx와 같음 |

- 재시도 간격: 0.5초, 1초 **(제 판단)**. 테스트에서는 0으로 주입할 수 있어야 한다.
- 분류는 로그 문자열이 아니라 오류 값으로 한다. 가짜 저장소(`StubBankingRepository`)로 모든 줄을 테스트할 수 있어야 한다. 분류 코드의 위치(모델, 저장소, Domain)는 빌더가 정한다.

**재시도 뒤 자동 조회 (사용자 결정: 조회만, 사용자 조작 없음)**

| 조회 결과 | 화면 |
|---|---|
| 200 (본문 정상) | 보냈어요 + 남은 잔액 |
| 200 + 디코딩 실패 | 보냈어요. 남은 잔액 줄 없음 |
| 404 | 송금 실패 "보내지 않았어요" |
| 전송 오류, 5xx, 그 밖의 오류 | 결과를 확인하지 못했어요 |

- 조회는 마지막 재시도 실패 직후 1번만 한다. 조회는 재시도하지 않는다 **(제 판단)**.
- "결과를 확인하지 못했어요"에서 "확인"으로 창을 닫으면 홈이 기존대로 잔액을 다시 불러온다. 사용자는 잔액으로 결과를 본다.
- 지금 실패 주입으로는 조회가 실패하지 않는다. 이 화면은 단위 테스트(가짜 저장소)로만 고정한다 **(제 판단)**.

### 6.5 화면 문구 **(제 판단)**

| 상태 | 제목 | 설명 | 버튼 |
|---|---|---|---|
| 보냈어요 | 보냈어요 | 남은 잔액 <금액> (영수증이 있을 때만) | 확인 |
| 송금 실패 | 송금 실패 | 이유 한 줄 (아래) | 확인 |
| 송금 중 (로딩) | 보내는 중이에요 | (스피너) | 없음 |
| 결과 모름 | 결과를 확인하지 못했어요 | 홈에서 잔액을 확인해 주세요. | 확인 |

송금 실패 이유:

| 원인 | 문구 |
|---|---|
| 400 | 금액을 확인해 주세요 |
| 404 | 계좌나 받는 사람을 찾을 수 없어요 |
| 그 밖의 4xx (422 등) | 요청을 처리할 수 없어요 |
| 자동 조회 결과 404 | 보내지 않았어요 |

- 기존 UI 테스트가 찾는 "송금 실패", "보냈어요" 문구는 유지한다.
- 결과 화면의 뒤로 가기 숨김은 그대로다.

### 6.6 로그

기존 규칙(`os.Logger`, subsystem `com.example.paylab`, 보간 값 `.public`, 레벨 기준)을 따른다. `transfer` 카테고리에 아래 내용을 남긴다. 문구 세부는 빌더가 정하고 `CLAUDE.md` 로그 표에 반영한다.

- 송금 시작 줄에 키를 추가
- 송금 중 재진입 무시
- 재시도 (몇 번째, 대기 시간, 원인)
- 2xx + 디코딩 실패를 성공으로 처리함
- 거절 (상태 코드)
- 자동 조회 시작 / 찾음 / 없음 / 실패(결과 모름)

### 6.7 테스트

**재현 테스트 먼저 (현재 코드에서 실패해야 한다)**
- `TransferModel`: `submit()`을 두 번 동시에 부르면 저장소 호출이 1번. 가짜 저장소가 첫 호출에서 멈춰 있는 동안 두 번째를 부른다 (바로 응답하면 두 번째가 첫 호출 뒤에 들어와 재현이 안 된다).
- `TransferModel`: 저장소가 디코딩 오류를 던지면 결과가 성공.

**단위: `FakeServer.handle` (DataKit, 병렬)**
- 키 헤더 없음 → 400, 잔액 그대로.
- 같은 키·같은 본문 두 번 → 같은 영수증, 잔액 한 번 차감.
- 같은 키·다른 본문 → 422, 잔액 그대로.
- 처리 뒤 잔액이 금액보다 작아진 상태에서 같은 키 재요청 → 200 + 저장된 영수증 (판정 순서 4 → 6 고정).
- `GET /transfers/<키>`: 있으면 200 + 영수증, 없으면 404.
- 실패 주입별 잔액: 처리 전 거절은 그대로, 응답 유실·깨진 응답은 한 번 차감.

**단위: `TransferModel` (가짜 저장소, 재시도 대기 0)**
- 결과 분류 표의 모든 줄.
- 재시도 요청이 모두 같은 키를 쓴다.
- 5xx 뒤 성공 → 보냈어요, 저장소 호출 2번.
- 5xx 3번 → 자동 조회 1번. 송금 요청 3번.
- 4xx → 재시도 없음.
- 자동 조회 표의 모든 줄. 조회가 송금 요청을 보내지 않는다. 4xx·성공에서는 조회하지 않는다.
- `proceedToConfirm()`마다 새 키.
- 끝난 뒤 송금 중 상태가 풀린다 (성공·실패·결과 모름 모두).

**통합 (`PayLabTests` 또는 `DataKitTests`의 직렬 Suite)**
- `RemoteBankingRepository`가 `Idempotency-Key` 헤더를 보낸다. 조회 404 → `nil`.
- 모델 → 저장소 → `URLSession` → 가짜 서버, 실패 주입 4가지 각각: 기대 화면 상태와 서버 잔액이 정확히 한 번 차감(또는 그대로).

**UI (`PayLabUITests`)** **(제 판단: 바꾸거나 추가하는 것 2개. 기존 성공 테스트 포함 모두 3개)**
- 기존 `--fail-transfer` 테스트 갱신: 로딩 → 송금 실패 "보내지 않았어요" → 홈 잔액 그대로.
- 신규: 응답 유실 매번 → 로딩("보내는 중이에요") → 보냈어요 → 홈 잔액 한 번 차감.
