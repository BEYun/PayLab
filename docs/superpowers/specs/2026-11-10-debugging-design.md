# 디버깅 용이성 설계 — PayLab

- 작성일: 2026-11-10
- 상태: 승인 완료 (2026-11-10)
- 브랜치: `claude/debugging-a7a6f0`
- 표기: **(제 판단)** = 사용자가 직접 정하지 않고 Claude가 정한 항목. 나머지는 사용자가 결정·승인한 항목.
- 선행 문서: `docs/superpowers/specs/2026-11-06-foundation-design.md`

## 1. 의도와 이유

PayLab에 버그가 생겼을 때 **Claude가 명령줄만으로 원인을 직접 찾고**, 사람은 그 보고를 확인한다. 이 장면을 가능하게 만드는 것이 이 세션의 목적이다.

### 사용자가 겪는 고충 (사용자 말을 정리)

1. **디코딩 불일치**: 서버가 보낸 데이터 타입이 코드의 모델 타입과 안 맞아 디코딩이 실패할 때, 무엇이 안 맞았는지 확인하기 어렵다.
2. **앱 멈춤(hang)·메모리 누수**: 원인 코드를 찾기 어렵다.
3. **메인 스레드 위반 크래시**: 메인 스레드에서 해야 할 작업을 다른 스레드에서 해서 앱이 죽는다.
4. **무반응·렌더링 실패**: 실제 테스트에서는 화면만 보므로, 반응이 없거나 화면이 안 그려진 원인을 알 수 없다.

### 현재 PayLab 상태 (코드 확인)

오류가 흔적 없이 사라지고, 로그가 하나도 없다.

| 위치 | 현재 동작 |
|---|---|
| `HomeModel.load` | `try?` → 실패하면 기존 목록 유지(처음엔 빈 목록). 이유는 남지 않음 |
| `TransferModel.loadRecipients` | `try?` → 빈 목록. 이유는 남지 않음 |
| `TransferModel.submit` | 어떤 오류든 `.failure`. 오류 내용은 버림 |
| `TransferModel.proceedToConfirm`, `submit` | `guard`에 걸리면 조용히 `return` |
| `RemoteBankingRepository.send` | `DecodingError`를 위로 던지지만 위에서 모두 삼킴 |

## 2. 목표

- **G1. 기록:** 화면 밖에서 일어난 일이 `os.Logger` 로그로 남고, Claude가 `log` 명령으로 읽을 수 있다.
- **G2. 절차:** 고충 4가지마다 Claude가 따라 할 조사 절차가 `CLAUDE.md` 디버깅 섹션에 있다.
- **G3. 검증:** 블라인드 연습으로 G1·G2가 실제로 쓸모 있는지 확인한다. 총 5회 (§6.3).

## 3. 비목표

| 하지 않는 것 | 이유·담당 |
|---|---|
| 평소 측정·자동 감지 (멈춤 감시기, 메모리 추적, 구간 계측) | 성능 세션. 이 세션은 "생겼을 때 원인 찾기"까지 (사용자 승인 경계) |
| 실패 처리, 재시도, 사용자에게 오류 문구 표시 | 트랜잭션 세션. 이 세션은 화면 동작을 바꾸지 않고 기록만 더한다 |
| 테스트 코드 작성 | 테스트 세션. 이 세션의 검증은 시뮬레이터 실행과 블라인드 연습으로 한다 |
| 외부 크래시 리포팅 SDK (Crashlytics, Sentry 등) | 사용자 결정: SDK 없이. 시뮬레이터 크래시 리포트 파일로 충분 |
| 앱 안 디버그 메뉴 | **(제 판단)** Claude는 화면 조작 대신 실행 인자로 앱을 띄운다. 메뉴가 있어도 쓸 일이 없다 |
| 연습용 버그 스위치를 앱 코드에 남기기 | **(제 판단)** 다른 세션 브랜치와 병합할 때 버그 코드가 섞이지 않게 |

## 4. 안티 목표 (돌아가도 실패로 보는 것)

- 로그는 많이 남는데 Claude가 그 로그만으로 원인을 못 짚는다. 블라인드 연습 실패를 원인 분석 없이 그대로 둔다.
- 기존 화면 동작이 바뀐다. 다른 세션이 기대하는 동작과 어긋난다.
- 로깅 래퍼 모듈, 로그 수집기 같은 추상화를 새로 만든다.
- 성능·트랜잭션·테스트 주제를 미리 구현한다.

## 5. 제약

- 환경: Xcode 27.2, iOS 27.0 시뮬레이터 런타임, Tuist 4.216.0, Swift 6 언어 모드.
- 외부 라이브러리 추가 금지 (사용자 결정).
- 시뮬레이터는 `CLAUDE.md` 명령대로 `PayLab-<브랜치>`를 쓴다. 이 브랜치 이름에는 `/`가 있지만, 시뮬레이터 생성·빌드·설치·실행이 모두 그대로 동작함을 확인했다 (2026-11-10). 인계 지침의 명령 수정은 하지 않는다.
- `CLAUDE.md`는 기존 줄을 건드리지 않고 `## 디버깅` 섹션만 추가한다. 테스트·CI 세션도 같은 파일을 고친다.
- 테스트 세션이 `HomeModel`, `TransferModel`에 테스트를 쓰고 있다. 이 두 파일의 수정은 로그 줄 추가로 한정해 병합 충돌을 줄인다.

## 6. 결정된 것

### 6.1 로그 (G1)

- `os.Logger`를 직접 쓴다. subsystem은 `com.example.paylab` **(제 판단)**.
- 모듈마다 자기 Logger를 한 줄로 선언한다. 공통 로깅 모듈은 만들지 않는다 **(제 판단: 모듈 하나 추가보다 subsystem 문자열 한 줄 중복이 단순)**.
- 카테고리 **(제 판단)**:

| 카테고리 | 모듈 | 남기는 것 |
|---|---|---|
| `app` | App | 앱 시작, 실행 인자(`--fail-transfer` 여부) |
| `network` | DataKit | 요청·응답·디코딩 실패·전송 오류 |
| `home` | HomeFeature | `HomeModel.load` 시작·성공(계좌 수)·실패(오류) |
| `transfer` | TransferFeature | `loadRecipients`·`select`·`proceedToConfirm`·`submit`의 시작·결과·실패, `guard`에 걸려 조용히 돌아간 경우 |

- **네트워크 로그는 `RemoteBankingRepository.send`에 붙인다. `FakeServerURLProtocol`에는 붙이지 않는다 (제 판단).**
  - 이유: `FakeServerURLProtocol`은 가짜 서버 자체다. 실제 서버로 바꾸면 사라진다. 앱이 계속 갖고 있을 클라이언트 쪽에서 기록해야 의미가 있다.
  - 덤: 기반 설계 §9가 경고한 "client 콜백이 `stopLoading` 뒤에 올 수 있음" 문제와 무관해진다.
- 네트워크 로그 내용:
  - 요청: 메서드, 경로.
  - 응답: 상태 코드, 걸린 시간(ms). 걸린 시간은 "무반응" 원인 구분용 맥락이다. 측정 체계가 아니다.
  - 응답 본문 원문: **DEBUG 빌드에서만** 남긴다 **(제 판단: 금융 앱에서 계좌·잔액 원문을 릴리스 로그에 남기지 않는 관행)**.
  - 디코딩 실패: 대상 타입, `DecodingError` 종류(typeMismatch / keyNotFound / valueNotFound / dataCorrupted), codingPath, debugDescription, 그리고 원문 본문(DEBUG).
  - 전송 오류: `URLError` 코드.
- 화면 모델의 기존 동작(`try?`, `.failure`)은 그대로 둔다. 오류를 삼키기 직전에 기록만 한다. `try?`를 `do/catch`로 바꾸는 것은 기록을 위한 최소 변경으로 허용한다.
- 레벨 **(제 판단)**: 정상 흐름은 `debug`/`info`, 실패는 `error`.
- 로그 문자열 보간은 `privacy: .public`으로 표시한다. 시뮬레이터 `log stream`에서 `<private>`로 가려지지 않게 하기 위해서다. 가짜 데이터라 노출해도 된다.

### 6.2 조사 절차 (G2) — `CLAUDE.md`의 `## 디버깅` 섹션

Claude가 그대로 복사해 실행할 수 있는 명령과 순서를 둔다. 유형별 뼈대:

- **공통 — 재현과 로그 읽기**
  - 앱 실행 전에 `xcrun simctl spawn <시뮬레이터> log stream --level debug --predicate 'subsystem == "com.example.paylab"'`를 백그라운드로 띄운다. 사후 조회는 `log show --last <기간>`.
  - 화면 조작이 필요하면 iOS 시뮬레이터 도구(탭·스크린샷)로 재현한다.
- **1 디코딩 불일치:** `network` 카테고리 `error` 줄 → codingPath·원문 확인 → Domain 모델 정의와 비교.
- **4 무반응·렌더링 실패:** 해당 화면 카테고리의 마지막 로그 → 어느 단계에서 멈췄는지(요청을 안 보냄 / 응답이 없음 / 실패를 삼킴 / `guard`에 걸림) 구분.
- **2 멈춤:** 멈춘 상태에서 앱 프로세스에 `sample`을 걸어 메인 스레드 스택을 본다.
- **2 메모리 누수:** 앱 프로세스에 `leaks`를 건다. 할당 위치가 필요하면 `MallocStackLogging`을 켜고 실행한다.
- **3 메인 스레드 위반:** `~/Library/Logs/DiagnosticReports`의 PayLab 크래시 리포트를 읽는다. 재현이 필요하면 Main Thread Checker나 Thread Sanitizer를 켜고 실행한다.

### 6.3 블라인드 연습 (G3)

- 횟수: 5회. 디코딩 불일치, 멈춤, 메모리 누수, 메인 스레드 위반, 무반응·렌더링 실패. 고충 2를 멈춤과 누수로 나눈다. 쓰는 도구가 다르고(`sample` / `leaks`·`heap`), 누수 쪽 도구가 가장 덜 검증됐기 때문이다 (사용자 승인).
- 역할:
  1. **출제 에이전트 A** (서브에이전트): 정해진 유형의 버그를 앱에 심고 빌드·설치한다. 두 가지를 남긴다.
     - **버그 신고:** QA가 화면에서 본 것만 적는다. 원인·위치·유형은 적지 않는다. 누수처럼 화면 증상이 없으면 사람이 관찰할 수 있는 현상으로 적는다 (예: "송금 창을 10번 열고 닫았더니 메모리 사용량이 계속 늘었다").
     - **정답:** 원인과 위치. 메인 세션에만 전달한다.
  2. **해결 에이전트 B** (새 서브에이전트): 버그 신고와 `CLAUDE.md`만 받는다. `git log`·`git diff`·`git status`와 정답은 보지 않는다. 두 단계로 일한다 (사용자 승인).
     - **1단계 (코드 안 봄):** 로그와 도구(`log`, `sample`, `leaks`·`heap`, 크래시 리포트, 시뮬레이터 탭·스크린샷)만 쓴다. "어느 화면, 어느 계층, 어느 함수"까지 용의 위치와 근거를 적어 고정한다.
     - **2단계:** 코드를 읽어 원인과 위치를 확정한다.
     - 이유: 앱 코드가 약 500줄이라, 처음부터 코드를 읽으면 로그 없이 코드 검토만으로 풀린다. 그러면 로그의 빈틈이 드러나지 않는다.
  3. **메인 세션:** 정답과 대조해 채점한다. 핵심 점수는 **1단계에서 얼마나 좁혔는가**다. 1단계에서 범위를 못 좁혔으면 2단계에서 맞혔어도 빈틈으로 보고 보강한다.
- 실패하면: 빈틈(무슨 로그나 절차가 없어서 못 찾았나)을 분석해 G1·G2를 보강한다. 같은 유형의 다른 버그로 1회 더 연습한다. 그래도 실패하면 사용자에게 보고한다 **(제 판단)**.
- 버그는 커밋하지 않고 작업 트리에서만 심는다. 연습 전에 작업 트리를 깨끗하게(커밋 완료) 만들고, 연습 후 되돌린다 **(제 판단)**.
- 버그는 앱 어디에 심어도 된다. 가짜 서버(`FakeServer`) 쪽 변경도 "서버가 응답을 바꿨다"는 현실적인 상황으로 인정한다.
- 유형 4에는 화면 모델은 정상인데 뷰가 그리지 못하는 버그도 포함한다 **(제 판단: 사용자 고충 4가 "렌더링 실패"를 명시)**. 뷰에는 로그를 미리 깔지 않는다. 모델 로그(데이터 도착)와 스크린샷(화면에 없음)을 대조해 "뷰 쪽 문제"로 좁히는 것을 절차로 둔다. 뷰 파일 수정은 연습 실패 후 보강이 꼭 필요할 때만 한다.
- 결과는 `docs/debugging-drills.md`에 기록한다 **(제 판단)**: 유형, 버그 신고, 정답, B의 보고, 성공 여부, 드러난 빈틈과 보강 내용.

## 7. 빌더에게 맡기는 것

- 로그 문구와 정확한 레벨 배분.
- 연습 순서와 각 연습의 구체적인 버그 내용 (출제 에이전트가 정한다).
- Main Thread Checker / Thread Sanitizer를 켜는 정확한 방법.
- `sample`·`leaks`에 넘길 프로세스 ID를 찾는 방법.
- `CLAUDE.md` 디버깅 섹션의 세부 문장.

## 8. 확인 안 된 가정 (구현 첫 단계에서 확인)

| 가정 | 틀렸을 때 |
|---|---|
| ~~`sample`이 시뮬레이터 앱 프로세스에 동작한다~~ | 확인함 (2026-11-10): Mac의 `sample <pid>`로 메인 스레드 콜 그래프가 나온다 |
| `leaks`가 누수 객체의 타입 이름을 보여 준다 | 일부 확인 (2026-11-10): `leaks <pid>`는 돌지만 "Process is not debuggable" 경고와 함께 기본 상태에서 타입 없는 `ROOT LEAK` 1개(32바이트)를 보고한다. `heap <pid>`는 Swift 타입별 인스턴스 수를 보여 준다. 실제 누수에서 타입 이름이 나오는지는 연습 때 확인하고, 안 나오면 `heap` 인스턴스 수 비교(동작 반복 전후)를 절차로 쓴다. 앱 시작 직후의 기본 누수는 잡음으로 적어 둔다 |
| `privacy: .public` 보간이 시뮬레이터 `log stream`에 그대로 보인다 | 보이게 하는 설정을 찾아 `CLAUDE.md`에 적는다 |
| ~~시뮬레이터 앱 크래시 리포트가 Mac의 `~/Library/Logs/DiagnosticReports`에 남는다~~ | 확인함 (2026-11-10): `PayLab-<날짜시각>.ips`(JSON)로 남는다 |
| (발견) 부팅 직후 `simctl launch`가 "No such process"로 실패한다 | `xcrun simctl bootstatus <시뮬레이터> -b`로 부팅 완료를 기다린 뒤 실행한다. `CLAUDE.md` 디버깅 섹션에 적는다 |
| ~~서브에이전트가 iOS 시뮬레이터 도구(탭·스크린샷)를 쓸 수 있다~~ | 확인함 (2026-11-10): 서브에이전트가 `mcp__Claude_Code_iOS_Simulator__control`을 불러올 수 있다 |

## 9. 완료 기준 (verify)

1. 빌드 성공, 기존 테스트 6개 통과.
2. 시뮬레이터에서 정상 송금과 `--fail-transfer` 실행 때 각 카테고리 로그가 `log stream`에 보인다. Claude가 직접 확인한다.
3. 블라인드 연습 5회 결과가 `docs/debugging-drills.md`에 있다. 유형마다 해결했거나, 빈틈과 보강 내용이 적혀 있다.
4. `CLAUDE.md`에 `## 디버깅` 섹션이 있다. 기존 줄은 그대로다.
5. 이 브랜치에 커밋. main 병합 여부는 사용자에게 묻는다.
