# 기반 단계 설계 — 토스 iOS 벤치마킹 샘플 앱

- 작성일: 2026-11-06
- 상태: 승인 완료 (2026-11-10)
- 표기: **(제 판단)** = 사용자가 직접 정하지 않고 Claude가 정한 항목. 나머지는 사용자가 결정·승인한 항목.

## 1. 의도와 이유

- 사용자는 토스 iOS 앱을 벤치마킹해서, Claude Code로 아래 5가지를 몸에 익히고 싶어 한다.
  1. 디버깅 용이성
  2. 테스트 코드 정착
  3. 자동 빌드 및 테스트
  4. 트랜잭션 관리
  5. 성능 개선 작업 자동화
- 토스 내부 코드는 볼 수 없다. 공개 자료(toss.tech 블로그, SLASH 발표)와 앱 UX를 참고해 **새 샘플 앱**을 직접 만든다.
- 5개 주제는 **각각 별도 Claude Code 세션**에서 진행한다.
- 이 문서는 그 전에 하는 **기반 단계**다. 목적은 모든 세션이 같은 앱 위에서 작업하도록 공통 바닥을 까는 것.

### 세션 진행 순서 (사용자 승인)

1. 기반 단계 (이 문서, 현재 세션)
2. 기반 완료 후 동시에: 디버깅 / 테스트 / CI — 세션마다 git 브랜치 분리
3. 테스트 세션 완료 후: 트랜잭션
4. CI 세션 완료 후: 성능 자동화

## 2. 목표

- 빌드되고 시뮬레이터에서 실행되는 최소 앱: 홈 + 송금 흐름.
- 이후 세션들이 브랜치에서 따로 작업한 뒤 충돌 적게 병합할 수 있는 구조.
- Claude Code가 Xcode 화면 조작 없이 명령줄만으로 생성·빌드·테스트·실행할 수 있는 상태.

## 3. 비목표 (각 주제 세션의 몫)

| 하지 않는 것 | 담당 세션 |
|---|---|
| 로깅, 디버그 메뉴, 크래시 리포팅 | 디버깅 |
| 실제 테스트 작성, 커버리지 | 테스트 |
| CI, fastlane, 배포, GitHub 원격 저장소 | CI |
| 송금 실패 처리, 재시도, 중복 송금 방지, 멱등성, 앱 종료 후 복구 | 트랜잭션 |
| 성능 측정, 계측 | 성능 |

- 실제 서버, 로그인·인증, 실제 금융 데이터는 전 단계에서 다루지 않는다.

## 4. 안티 목표 (돌아가도 실패로 보는 것)

- 기반 단계가 뒤 세션의 주제를 미리 구현해 버림. 예: 로거 모듈, 재시도 로직을 미리 만들어 둠. → 각 세션에서 배울 게 사라진다.
- Tuist가 생성하는 `.xcodeproj` / `.xcworkspace`를 git에 커밋함. → 브랜치 병합 때 충돌.
- 빌드·테스트에 Xcode 화면 조작이 필요한 구조. → Claude Code 자동화가 막힌다.

## 6. 결정된 것

### 앱 기능 (사용자 승인)

- **홈:** 내 계좌 목록과 잔액.
- **송금:** 받는 사람 선택 → 금액 입력 → 확인 → 결과.
- **서버 없음:** 앱 안의 가짜 서버가 응답, 지연, 실패를 흉내 낸다.
- 송금을 고른 이유: 트랜잭션·디버깅·성능 세션이 모두 이 흐름을 재료로 쓴다.

### 송금 완성도: "일단 동작" (사용자 승인)

- 정상 경로 완주: 받는 사람 선택 → 금액 입력 → 확인 → 송금 요청 → 성공 화면 → 홈 복귀 시 잔액 반영.
- 출금 계좌: 홈의 계좌 행에서 송금을 시작하고, 그 계좌를 출금 계좌로 쓴다. 계좌 선택 단계는 추가하지 않는다. App이 Home → Transfer로 넘기는 값은 출금 계좌 하나. **(제 판단)**
- 금액 입력 최소 검증: 0원 이하, 출금 계좌 잔액 초과면 다음 단계로 못 감. **(제 판단)**
- 실패 응답이 오면 결과 화면에 "실패"만 표시. 재시도·중복 방지·복구 없음.

### 기술 (Claude 제안 → 사용자 승인)

- UI: SwiftUI
- 최소 지원 iOS: 18
- 프로젝트 생성: Tuist (Homebrew로 설치). 이유: 브랜치 병합 시 `.xcodeproj` 충돌 회피.
- Swift 6 언어 모드 **(제 판단)**: 새 프로젝트라 처음부터 엄격한 동시성 검사로 시작.

### 모듈 (Claude 제안 → 사용자 승인)

- App / Feature(Home, Transfer) / Domain / Data / DesignSystem

의존 방향 **(제 판단)**:

```text
App ──> HomeFeature ─────┐
 │  └─> TransferFeature ─┼──> Domain <── Data
 │                       └──> DesignSystem
 └────> Data   (App이 Data 구현체를 만들어 Feature에 주입)
```

- **Domain:** 순수 Swift. 모델(계좌, 받는 사람, 송금)과 저장소 프로토콜. UI·네트워크 의존 없음.
- **Data:** Domain 프로토콜 구현 + 가짜 서버.
- **Feature 간 직접 의존 금지.** Home → Transfer 이동은 App이 조립한다. 이유: 세션별 병렬 작업 시 결합 최소화.
- **화면 로직은 뷰와 분리된 `@Observable` 모델에 둔다.** 이유: 테스트 세션이 UI 없이 로직을 테스트할 수 있어야 한다.

### 가짜 서버 (제 판단)

- 앱은 **실제 `URLSession`으로 요청**하고, 커스텀 `URLProtocol`이 요청을 가로채 메모리 속 가짜 서버가 JSON으로 응답한다.
  - 이유: 디버깅 세션의 네트워크 로거, 성능 세션의 구간 측정이 실제 네트워크 계층을 대상으로 해야 의미가 있다. 저장소 프로토콜을 메모리 구현으로 바로 채우면 이 계층이 아예 없다.
- 데이터: 계좌 2~3개, 받는 사람 몇 명. 메모리에만 존재 (앱 재시작 시 초기화).
- 송금 성공 시 출금 계좌 잔액 차감.
- 응답 지연: 기본값 수백 ms, 코드에서 조정 가능.
- 실패 주입: 앱 실행 인자 하나로 켠다. 켜면 송금 요청만 실패한다. 기본 꺼짐. 실패 처리는 트랜잭션 세션 몫이고, 여기서는 스위치만 둔다. 앱 안의 토글·디버그 메뉴는 만들지 않는다 (디버깅 세션 몫). **(제 판단)**

### 테스트 타깃 (사용자 승인: 빈 껍데기)

- 모듈마다 테스트 타깃 하나.
- 각 타깃에 형식적 테스트 1개 (Swift Testing). 목적: 테스트 명령이 실제로 도는지 확인. **(제 판단)**
- 실제 테스트, 프레임워크 최종 선택은 테스트 세션 몫.

### 저장소 (사용자 승인)

- 이 설계 문서도 첫 커밋에 포함.

## 9. 다음 세션 인계 메모

- **디버깅:** 네트워크 로거는 `URLProtocol` 계층에 붙이면 된다.
  - `FakeServerURLProtocol`의 client 콜백은 `startLoading`을 부른 스레드가 아니라 백그라운드 Task에서 실행된다. 이론상 `stopLoading` 뒤에 도착할 수 있다. 이 계층에 계측을 붙일 때 확인할 것.
- **테스트:** Domain 모델과 Feature의 `@Observable` 모델이 첫 대상.
  - 가짜 서버 등록은 프로세스 전역이다(`FakeBackend.makeSession`). 서로 다른 `FakeServer` 설정을 쓰는 테스트가 동시에 돌면 서로 간섭한다. Swift Testing은 기본이 병렬 실행이다. 세션별 바인딩이나 직렬 실행은 해당 세션이 결정한다.
- **CI:** GitHub 원격 저장소 생성 여부부터 결정.
- **트랜잭션:** "트랜잭션"의 의미부터 결정 — 송금 정합성 / APM 구간 추적 / 로컬 DB.
  - 가짜 서버 등록은 프로세스 전역이다(`FakeBackend.makeSession`). 서로 다른 `FakeServer` 설정을 쓰는 테스트가 동시에 돌면 서로 간섭한다. Swift Testing은 기본이 병렬 실행이다. 세션별 바인딩이나 직렬 실행은 해당 세션이 결정한다.
- **성능:** CI 세션 이후 시작.
