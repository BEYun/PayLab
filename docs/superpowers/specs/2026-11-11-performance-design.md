## 1. 의도와 이유

- 사용자가 정한 "성능 개선 작업 자동화"의 뜻: **테스트와 빌드 중에 생긴 성능 문제를 자동으로 찾아 기록하고, "해야 할 작업"으로 정리한다.**
  - 대상: 크래시, UI hang, 빌드 시간.
  - 정리 방식: 문제 하나 = GitHub 이슈 하나.
  - 고치는 건 사람이다. 사용자가 이슈 목록을 보고 할 일을 골라 수정하고 PR을 연다.
- 핵심 원칙 (사용자 결정)
  - **기존 문제**(지금 커밋하려는 변경과 무관) → 이슈로 남긴다.
  - **이번 변경의 문제** → 이슈로 만들지 않는다. 코드가 아직 바뀔 수 있기 때문이다. 그 자리에서 막거나 알리고, 그 작업 안에서 고친다.
- 성공 기준
  1. 기존 문제는 빠짐없이 이슈가 된다. 같은 문제는 이슈 하나에 모인다.
  2. 이번 변경이 만든 hang·느린 함수는 PR 전에, 커밋 단계에서 잡힌다.
  3. 사용자는 이슈만 읽고 무엇을 어디서 고칠지 안다.
- 지금 상태 (2026-11-11 측정)
  - hang: 어디에도 기록되지 않는다. 디버깅 절차에 "멈춤" 조사법(`sample`)만 있다.
  - 크래시: 테스트 실패와 `.ips` 리포트로만 남는다. 모아서 관리하지 않는다.
  - 빌드 시간: 측정·기록하지 않는다.
  - CI 빌드 단계(성공 14회): 164~426초. 코드가 거의 같아도 크게 흔들린다. 예: 문서만 바꾼 PR #5는 211초, 같은 내용의 main 병합은 255초.
  - CI 빌드 단계 376초의 분해 (main, 2026-11-11 06:15 실행)

    | 구간 | 시간 |
    |---|---|
    | `xcodebuild` 실행 → 첫 출력("Command line invocation") | 263초 |
    | 의존 그래프·준비 | 23초 |
    | 실제 빌드 (시스템 모듈 PCM 63개 + 우리 코드 컴파일) | 약 74초 |

    같은 잡의 두 번째 `xcodebuild`(테스트)는 8초 만에 시작한다. 263초는 러너에서 처음 부르는 `xcodebuild`만 겪는 비용이다.
  - 로컬 클린 빌드 (새 DerivedData, `build-for-testing`): 5.5초. 우리 코드 `SwiftCompile` 31개 합 23초(CPU).
  - 타입 검사: 로컬에서 가장 느린 함수 66ms(Swift Testing 테스트 함수). 100ms를 넘는 함수는 없다.

## 2. 목표

1. **hang 감지:** 앱 안 감시자가 메인 스레드가 오래 막힌 것을 잡아 로그와 메인 스레드 스택을 남긴다.
2. **크래시 수집:** 테스트·확인 중 생긴 PayLab 크래시 리포트를 모은다.
3. **빌드 측정:** 느린 함수(컴파일러 경고)를 로컬·CI 빌드에서 잡는다. CI에서 우리 코드 컴파일 시간과 전체 빌드 시간을 기록한다.
4. **판정:** 각 문제가 이번 변경의 문제인지, 기존 문제인지 가른다.
5. **보고:** 기존 문제는 GitHub 이슈, 이번 변경의 문제는 커밋 차단(로컬) 또는 PR 코멘트(CI).
6. **재료:** hang을 재현할 "거래 내역" 화면을 새로 넣는다.
7. **절차:** `CLAUDE.md`에 성능 섹션을 쓴다. Claude가 시뮬레이터 확인 뒤에도 같은 보고를 돌릴 수 있게 한다.
8. **테스트:** `CLAUDE.md` 테스트 규칙대로 단위·통합·UI 테스트와 스크립트 테스트를 함께 쓴다.

## 3. 비목표

| 하지 않는 것 | 이유 |
|---|---|
| 문제 자동 수정 | 고치는 건 사용자다 |
| 지금 CI 빌드의 느림(`xcodebuild` 첫 출력까지 263초) 줄이기 | 이번 범위는 측정·기록 체계다. 고치는 대신 측정값과 함께 이슈 하나로 남긴다(§6.13) **(제 판단)** |
| 천천히 느는 빌드 시간 감지("한 달 전 대비") | 필요해지면 나중에 추가 (사용자 확인) |
| 앱 실행 시간, 메모리, 스크롤 프레임 드랍(hitch) | 사용자가 고른 대상은 크래시·hang·빌드 시간이다 |
| 실기기 측정, MetricKit | 시뮬레이터·CI 범위 **(제 판단)** |
| 외부 라이브러리, 외부 크래시 수집 서비스 | 스파이크로 외부 라이브러리 없이 메인 스레드 스택을 잡을 수 있음을 확인했다 **(제 판단)** |
| UI 테스트를 CI에 넣기 | CI 시간이 늘어난다. UI 경로의 hang은 로컬 커밋 hook이 잡는다 **(제 판단)** |
| Release 빌드에서 hang 감시 | 테스트·확인은 모두 Debug 빌드다 **(제 판단)** |
| 송금 결과를 거래 내역에 반영 | 거래 내역은 hang 재료다. 송금 흐름은 건드리지 않는다 **(제 판단)** |
| 비공개 이슈 관리 | 코드·데이터가 이미 공개·가짜다. 컴퓨터 정보만 지우고 공개 이슈로 둔다 (사용자 결정) |

## 4. 안티 목표 (돌아가도 실패로 보는 것)

- 작업 중인 변경의 문제가 공개 이슈로 쌓인다.
- 기존 문제가 기록 없이 사라진다. 또는 같은 문제로 이슈가 여러 개 생긴다.
- 러너 속도 흔들림 때문에 가짜 빌드 시간 이슈·코멘트가 쏟아진다.
- 이슈·코멘트에 개인 경로, 사용자 이름, 컴퓨터 이름, 시뮬레이터 UDID, 메일, 토큰이 들어간다.
- 일부러 넣은 hang·느린 함수가 main에 남는다. 이것들은 구현 중 커밋 단계에서 잡혀야 한다 (사용자 지적).
- 이슈 생성이 실패했다고 커밋이 막힌다. (네트워크·`gh` 인증 문제는 문제 보고를 막을 뿐, 작업을 막지 않는다.)
- 거래 내역 화면에 결과를 보려고 한 번 더 누르는 단계가 생긴다.

## 5. 제약

- 공개 저장소다. 커밋 기록 전체에 키·토큰·개인 경로가 없어야 한다.
- 외부 라이브러리 추가 금지.
- 모듈 경계: Feature끼리 import 금지. Domain은 SwiftUI·네트워크 import 금지. 화면 로직은 `@Observable` 모델에 두고 뷰는 표시만 한다.
- `BankingRepository`가 바뀌면 `HomeFeature`·`TransferFeature`의 `StubBankingRepository`를 둘 다 맞춘다.
- 커밋 hook(`.claude/hooks/require-tests-before-commit.sh`)은 `scripts/test-all.sh`가 실패하면 커밋을 막는다. hook을 끄거나 우회하지 않는다. hook 시간 상한은 600초다.
- 병렬 세션이 시뮬레이터를 따로 쓴다(`PayLab-<브랜치>`). 크래시 리포트 폴더(`~/Library/Logs/DiagnosticReports`)는 공용이라 시뮬레이터 UDID로 거른다.
- CI: GitHub 러너 `xcode-27`, Xcode 27.2. PR 코드를 빌드·실행하는 잡에는 쓰기 권한을 주지 않는다 **(제 판단)**.
- Swift 6, iOS 18 이상, Swift Testing(단위·통합), XCTest(UI).
- `CLAUDE.md`는 다른 세션도 고친다. 이번에는 `## 성능` 섹션을 새로 쓰고, 기존 줄은 동작이 바뀐 곳만 고친다.

## 6. 결정된 것

### 6.1 문제 종류와 기준

| 종류 | 감지 | 비정상 기준 | 어디서 |
|---|---|---|---|
| `crash` | 시뮬레이터 크래시 리포트(`.ips`) | PayLab 프로세스 크래시 | 로컬, CI |
| `hang` | 앱 안 감시자 → `hang` 로그 | 메인 스레드가 **250ms 이상** 응답 없음 **(제 판단: Apple의 hang 기준)** | 로컬, CI |
| `slow-build` (느린 함수) | 컴파일러 경고 `-warn-long-function-bodies`, `-warn-long-expression-type-checking` | 타입 검사 **100ms 초과** (사용자 동의) | 로컬, CI 빌드 |
| `slow-build` (컴파일 시간) | CI `build-for-testing`의 빌드 타이밍 요약 | 우리 코드 컴파일 시간이 main 최근 5회 중앙값보다 **30% 이상, 그리고 N초 이상** 늘어남 (사용자 동의) | CI만 |
| (기록만) 전체 빌드 단계 시간, `xcodebuild` 첫 출력까지 시간 | CI 단계 시각 | 이슈 없음. 추세만 기록 (사용자 동의) | CI main |

- "로컬" = `scripts/test-all.sh`(커밋 hook 포함)와, Claude의 시뮬레이터 확인 뒤 수동 실행(§6.7).
- 느린 함수 기준 100ms는 로컬 최대 66ms 기준이다. CI 러너가 더 느려 기존 함수가 100ms를 넘으면, 그 값보다 여유 있게 올린다. 첫 PR의 CI 측정으로 확인한다 **(제 판단)**.
- 느린 함수 경고 플래그는 `Project.swift`의 Debug 설정에 넣는다. 로컬 Xcode 빌드에서도 경고가 보인다 **(제 판단)**.
- 스택에 우리 코드 함수가 하나도 없는 hang은 무시한다. 기록 파일에만 남긴다 (사용자 동의). 시뮬레이터가 바쁠 때 생기는 가짜 hang을 줄이기 위해서다.
- "우리 코드" = 이 저장소 소스에서 나온 함수(앱, 모듈, 테스트) **(제 판단)**. 기호화한 파일 경로가 저장소 안이면 우리 코드다.
  - 예외: 컴파일러가 만든 진입점(`main`, `PayLabApp.$main()` 등)은 뺀다. 메인 스레드 스택에는 늘 있어서, 넣으면 모든 hang이 "우리 코드 있음"이 되고 `PayLabApp.swift`를 고친 변경은 모든 hang과 엮인다.

### 6.2 hang 감시자

- 위치: App 타깃 **(제 판단)**. 앱 전체를 감시하는 조립 계층 일이라서다. Feature·DataKit은 모른다.
- Debug 빌드에서만 켠다 **(제 판단)**. 단위 테스트 호스트(`PayLabTests`의 `TEST_HOST` = PayLab 앱)에서도 돈다.
- 동작
  1. 백그라운드 스레드가 주기적으로 메인 큐에 신호를 보낸다.
  2. 250ms 안에 메인이 응답하지 않으면 hang 시작이다. 그 순간 메인 스레드 스택을 잡는다.
     - 방법: 메인 스레드를 잠깐 멈추고 레지스터를 읽어 프레임 포인터를 따라간다(`thread_suspend` → `thread_get_state` → `thread_resume`).
     - 스파이크(macOS arm64, Swift)로 감시 스레드에서 메인 스레드의 정렬 함수 스택을 잡는 것을 확인했다.
  3. 메인이 응답하면 hang 끝이다. 지속 시간과 시작 때 잡은 스택을 로그로 남긴다.
  - hang 한 번에 기록 한 번. 같은 hang 동안 반복 기록하지 않는다.
- 로그: 카테고리 `hang`, 레벨 error **(제 판단: error 레벨은 따로 설정 없이 `log show`에 남는다)**.
  - 요약 줄: 지속 시간, hang 번호.
  - 프레임 줄: 프레임마다 한 줄 **(제 판단: 로그 한 줄 길이 제한 때문)**. 나중에 파일:줄로 기호화할 수 있는 정보(이미지, 주소, 이미지 로드 주소)를 담는다.
- 기호화는 보고 스크립트가 빌드 결과물로 한다(`atos` 등). 앱은 주소만 남긴다.
- 감시자 자체 테스트(일부러 메인을 막는 테스트)는 앱 전역 감시자의 `hang` 로그를 남기지 않게 한다 **(제 판단)**. 남기면 그 테스트가 매번 보고 대상이 된다.

### 6.3 크래시 수집

- 대상: `~/Library/Logs/DiagnosticReports/PayLab-*.ips` 중 이번 실행의 시뮬레이터 UDID이고, 실행 시작 시각 이후인 것.
- `scripts/crash-summary.py`의 읽기 방식(첫 줄 헤더 JSON, 크래시 스레드 프레임)을 따른다.
- 크래시는 테스트도 실패시킨다. 그래서 크래시가 나면 지금처럼 커밋이 막히고 CI가 실패한다. 이 동작은 그대로 둔다.
- 테스트가 실패해도 수집·보고는 돌아야 한다. 기존 크래시를 이슈로 남기기 위해서다.

### 6.4 빌드 측정 (CI)

- `build-for-testing`에 빌드 타이밍 요약(`-showBuildTimingSummary`)을 켠다.
- 측정값

  | 이름 | 뜻 |
  |---|---|
  | 우리 코드 컴파일 | `SwiftCompile`(우리 타깃) 합 |
  | 시스템 모듈 준비 | `SwiftExplicitDependency…` 작업 합 |
  | 정규화 값 | 우리 코드 컴파일 ÷ 시스템 모듈 준비 |
  | `xcodebuild` 첫 출력까지 | 빌드 단계 시작 → "Command line invocation" |
  | 전체 빌드 단계 | 단계 시작 → 끝 |

- 정규화 (추측): 시스템 모듈 준비는 매번 같은 일이다. 그래서 그 시간으로 나누면 러너 속도 차이가 상쇄될 것이다. main 기록이 쌓이면 흔들림을 비교한다. 효과가 없으면 우리 코드 컴파일 시간을 그대로 쓴다 **(제 판단)**.
- 판정: 정규화 값이 main 최근 5회 중앙값보다 30% 이상 크고, 우리 코드 컴파일 시간이 N초 이상 늘었을 때만 비정상.
  - N 시작값: 10초 **(제 판단)**. main 기록의 흔들림 폭을 보고 조정한다.
  - main 기록이 5회 미만이면 판정하지 않고 기록만 한다 **(제 판단)**.
- 저장: main push 실행마다 측정값을 Actions artifact로 올린다 **(제 판단)**. 별도 저장소·브랜치가 필요 없다. PR 실행은 최근 main 5회 artifact를 읽는다.

### 6.5 판정: 이번 변경의 문제인가, 기존 문제인가

- 변경 파일
  - 로컬: `origin/main`과의 merge-base 이후 커밋된 변경 + 스테이징된 변경 + 스테이징 안 된 변경 + 추적 안 하는 새 파일. `git fetch`는 하지 않는다 **(제 판단)**.
  - CI PR: PR의 base와 head 차이.
  - CI main push: 판정하지 않는다. main은 공유 코드라 모든 문제가 기존 문제다 (사용자 동의: "병합돼 main에서도 증가 → 이슈").
- 문제의 위치 파일
  - crash, hang: 스택의 **모든** 우리 코드 프레임의 파일. 맨 위만 보지 않는다. A 파일을 고쳐 B 파일 함수가 느려져도 보통 A가 호출 스택에 남는다.
  - 느린 함수: 경고가 가리킨 파일.
  - 컴파일 시간: 위치 파일이 없다. PR에서는 이번 변경의 문제, main에서는 기존 문제.
- 규칙: 위치 파일 중 하나라도 변경 파일이면 → 이번 변경의 문제. 아니면 → 기존 문제.
- 스택에 우리 코드가 없는 크래시는 기존 문제로 본다 **(제 판단)**. 변경과 연결할 근거가 없다.
- 알려진 한계: 변경이 스택에 남지 않는 방식으로 문제를 만들면(예: 데이터 양만 늘림) 기존 문제로 잘못 판정한다. 이슈에 발견한 브랜치·커밋을 적어, 사용자가 보고 닫을 수 있게 한다.
- 로컬의 느린 함수 검사는 **변경된 Swift 파일만** 본다 **(제 판단)**.
  - 증분 빌드는 이미 컴파일된 파일을 다시 컴파일하지 않는다. 경고가 안 나오면 막힌 커밋을 그냥 다시 시도해도 통과해 버린다.
  - 그래서 `test-all.sh`가 빌드 전에 변경된 Swift 파일을 다시 컴파일되게 만든다(수정 시각 갱신 등). 다른 파일의 경고는 로컬에서 무시한다.
  - 기존 느린 함수는 CI가 잡는다. PR CI는 클린 빌드라 모든 파일이 컴파일되고, PR과 무관한 느린 함수는 기존 문제로 이슈가 된다.

### 6.6 보고

| 어디서 | 이번 변경의 문제 | 기존 문제 |
|---|---|---|
| 로컬 `test-all.sh` (커밋 hook 포함) | 실패로 끝남 → **커밋 차단** (hang, 느린 함수. 크래시는 원래 테스트 실패로 차단) (사용자 결정) | 이슈 생성·덧붙임. 이것만으로는 차단하지 않음 |
| CI PR | PR 코멘트 (사용자 동의) | 이슈 |
| CI main push | 없음 | 이슈 |

- 이슈 (공개 GitHub 이슈, 사용자 결정)
  - 라벨: `crash`, `hang`, `slow-build` 중 하나 + 자동 생성 표시 `perf-auto` **(제 판단)**. 라벨이 없으면 만든다.
  - 제목: 종류, 우리 코드 함수, 크기 **(제 판단)**. 예: `[hang] HistoryModel.load() 412ms`.
  - 본문: 종류와 수치, 처음 발견한 곳(로컬/CI, 브랜치, 커밋, CI 실행 링크), 재현 단서(테스트 이름을 알 수 있으면 테스트 이름, 아니면 hang 직전 앱 로그 몇 줄), 우리 코드 스택(함수, 파일:줄), 원문 일부, 숨은 서명 표식.
  - 같은 서명의 **열린** 이슈가 있으면 새 이슈를 만들지 않고, 그 이슈 본문의 "발생 기록"을 고친다 **(제 판단)**.
    - 발생 기록: 횟수, 마지막 발견 시각, 최근 발견한 곳 몇 개(로컬/CI, 브랜치, 커밋).
    - 코멘트는 달지 않는다. 오래된 문제 하나가 커밋 시도·PR push·main push마다 공개 코멘트와 알림을 만들기 때문이다.
  - 같은 서명의 **닫힌** 이슈만 있으면 **(제 판단)**
    - CI: 새 이슈를 만든다(고쳤다가 다시 생긴 문제). 본문에 이전 이슈를 링크한다. PR CI는 main과 합친 코드를 빌드하므로 main의 수정이 들어 있다.
    - 로컬: 이슈를 만들지 않고 출력만 한다. 오래된 main에서 갈라진 브랜치는 이미 고쳐진 문제를 그대로 갖고 있어, 만들면 브랜치마다 가짜 재발 이슈가 생긴다.
- 서명 **(제 판단)**
  - crash: 예외 종류 + 가장 안쪽 우리 코드 함수.
  - hang: 가장 안쪽 우리 코드 함수.
  - 느린 함수: 파일 + 함수 이름. 줄 번호는 넣지 않는다. 줄이 밀려도 같은 문제로 본다.
  - 컴파일 시간: 하나로 고정. 열린 이슈 하나에 계속 덧붙인다.
- 올리기 전 지우는 정보: 홈 폴더 경로(→ `~`), 러너 작업 경로(→ 저장소 기준 상대 경로), 시뮬레이터 UDID, 컴퓨터 이름, 메일 주소, 토큰 형태의 문자열.
- PR 코멘트: PR마다 코멘트 하나를 고쳐 쓴다 **(제 판단)**. 이번 변경의 문제 목록과 수치.
- `gh` 인증 실패·네트워크 오류: 로컬은 경고만 출력하고 넘어간다. 보고 내용은 `.build/` 아래 파일로 남긴다 **(제 판단)**.

### 6.7 로컬 흐름

- `scripts/test-all.sh`
  1. 시작 시각을 기록한다.
  2. 기존 단계(생성 → 시뮬레이터 → 단위·통합 → UI → hook 테스트)를 돈다.
  3. 테스트 성공·실패와 상관없이 마지막에 수집 → 판정 → 보고를 돈다.
  4. 이번 변경의 hang·느린 함수가 있으면 실패로 끝난다. 원래 실패(테스트)는 원래대로 실패다.
  - 마지막 줄 `ALL TESTS PASSED` 규칙은 그대로 둔다.
- Claude의 시뮬레이터 확인: 확인 시작 시각부터의 hang·크래시를 같은 보고 스크립트로 처리한다. 명령은 `CLAUDE.md` `## 성능`에 적는다.
- 보고 스크립트는 비교 기준을 바꾸는 옵션을 둔다 **(제 판단)**. 기본은 `origin/main` merge-base다. 시연·테스트에서는 "변경 파일 없음"으로 돌릴 수 있다(§6.10).

### 6.8 CI

- `build-and-test` (macOS, 기존 잡)
  - `build-for-testing`에 타이밍 요약을 켠다. 느린 함수 경고는 `Project.swift` 설정으로 따라온다.
  - 테스트 뒤, 성공·실패와 상관없이: 크래시 리포트, CI 시뮬레이터의 `hang` 로그, 빌드 로그의 느린 함수 경고, 측정값을 모은다. 기호화(파일:줄)까지 여기서 한다. 결과를 artifact로 올린다.
  - 권한은 지금처럼 읽기만.
- 새 보고 잡 (ubuntu) **(제 판단)**
  - `build-and-test` 뒤에 성공·실패와 상관없이 돈다. 취소되면 돌지 않는다.
  - artifact와 최근 main 측정값을 읽고 판정한다. 이슈·PR 코멘트를 쓴다.
  - 권한: `issues: write`, `pull-requests: write`, `actions: read`.
  - PR에서는 기존 Claude 잡처럼 소유자 PR만 돈다 **(제 판단)**.
- CI 시간 증가는 수집·기호화·보고 잡을 합쳐 1분 안쪽이어야 한다 **(제 판단)**.

### 6.9 재료: 거래 내역 화면 **(제 판단, 화면 추가는 사용자 동의)**

- 진입: 홈의 계좌 행을 누르면 그 계좌의 거래 내역으로 간다. "송금" 버튼은 그대로다.
- 위치: `HomeFeature` 안 (`HistoryModel` + 뷰). 새 모듈을 만들지 않는다. 홈에서 바로 이어지는 화면이라 App 연결이 필요 없다.
- 데이터
  - Domain: 거래 모델(번호, 시각, 내용, 금액 ±) + 저장소에 "계좌의 거래 내역 조회".
  - 가짜 서버: 계좌별 거래 내역 경로. 계좌마다 수천 건을 정해진 규칙으로 만든다(실행마다 같은 결과).
  - 송금은 거래 내역에 반영하지 않는다(비목표).
- 화면: 날짜별로 묶은 목록, 각 줄에 내용·시각·금액. 표시만 한다.
- 로그: 카테고리 `history`. `load start` / `load ok count=<n>` / `load failed`. 기존 로그 규칙(레벨, `.public`)을 따른다.
- 구현 중 시연 (사용자 지적: 일부러 넣은 문제는 PR 전에 잡혀야 한다)
  1. 처음에는 흔한 실수로 만든다: 메인 스레드에서 수천 건 정렬·날짜 포맷(줄마다 포맷터 생성). 매번 250ms를 넘게 데이터 양을 맞춘다.
  2. `test-all.sh`가 "이번 변경의 hang"으로 실패해 커밋이 막히는지 확인한다.
  3. 무거운 일을 메인 밖으로 옮기고 포맷터를 재사용해 고친다. 통과를 확인한다.
  4. 느린 함수도 같다: 타입 검사가 느린 식을 넣어 막히는지 확인하고 고친다.
  - 실수 버전은 커밋되지 않는다(hook이 막는다). main에 남지 않는다. 막힌 출력은 PR 설명에 기록한다.

### 6.10 시연: 기존 문제 → 이슈 (사용자 동의)

- 이번 변경의 hang은 hook이 커밋을 막는다. 그래서 "hang을 임시 커밋으로 기존 문제로 만들기"는 hook 우회 없이는 못 한다.
- 대신 **(제 판단)**: hang이 든 작업 트리에서 보고 스크립트를 "변경 파일 없음"으로 돌린다. 그 hang이 기존 문제로 판정돼 실제 이슈가 생기는지 확인한다.
- 확인 뒤 이슈는 닫고(`perf-auto` 라벨, "시연" 표시), 작업 트리는 되돌린다. 공개 저장소에 닫힌 시연 이슈 하나가 남는다.
- 같은 방식으로 "같은 문제 재발 → 기존 이슈에 덧붙임"도 한 번 확인한다.

### 6.11 `CLAUDE.md` `## 성능`

- 문제 종류·기준 표, 판정 규칙, 이슈 라벨·서명.
- 로컬: `test-all.sh`가 막았을 때 읽는 곳(보고 파일, hang 스택), 시뮬레이터 확인 뒤 보고 명령.
- CI: 측정값 읽는 법(artifact, 잡 요약), PR 코멘트·이슈가 생기는 조건.
- 기존 `## 디버깅`의 "멈춤", "크래시" 절차와 연결한다(이슈의 스택 → 그 절차로 원인 조사).
- 테스트 개수, 로그 표(`hang`, `history` 카테고리)를 갱신한다.

### 6.12 테스트

| 단계 | 대상 |

### 6.13 첫 이슈: CI `xcodebuild` 시작 대기 **(제 판단)**

- §1의 측정(첫 `xcodebuild`가 출력까지 263초, 실제 컴파일 약 74초)을 `slow-build` 이슈 하나로 남긴다.
- 자동 규칙(증가 감지)으로는 생기지 않는 기존 문제라 손으로 만든다. 사용자가 이슈 목록에서 고를 첫 빌드 속도 작업이 된다.
- 본문: 단계별 시간, 근거가 된 CI 실행 링크, 두 번째 `xcodebuild`는 8초 만에 시작한다는 사실. 원인 추측은 추측이라고 적는다.
